# Markdown Workspace 仕様書

- 文書版: 0.1
- 状態: MVP実装開始版
- 目的: NAS上のMarkdownを唯一の正本として、PC・Android・自作Webアプリから同じデータを扱う
- 最優先: 既存Markdown資産を壊さないこと、入力の反応を通信速度から切り離すこと

## 1. プロダクト方針

### 1.1 解決する問題

Obsidian VaultをNAS上に直接置いた結果、キー入力やアプリ起動に遅延が発生している。一方で、NAS上のMarkdownをAndroidアプリ・Webアプリ・自作サービスが直接利用しているため、端末ごとのローカル複製と同期ソフトを前提にした構成には戻さない。

### 1.2 基本原則

1. NAS上のMarkdownファイルが唯一の正本（Single Source of Truth）。
2. クライアントは入力・表示を担当し、NASへのI/Oはサーバーが担当する。
3. キー入力処理はネットワークI/Oを待たない。
4. 未保存編集はブラウザのIndexedDBに永続化し、通信復旧後に再送する。
5. 保存確認前にローカル変更を破棄しない。
6. 既存Markdownを可能な限りそのまま維持し、未知の構文・Frontmatter・リンクを勝手に正規化しない。
7. 同期フォルダや定期的な端末間コピーは採用しない。

## 2. 想定ユーザー・利用環境

- 主端末: Windowsブラウザ
- 副端末: Androidブラウザ / 将来の専用アプリ
- サーバー: 常時稼働WindowsミニPC（将来Linux移行も可能）
- ファイル保管: NAS共有フォルダ
- 外部接続: Tailscale等のプライベートネットワークを想定。NASやAPIを直接インターネット公開しない。

## 3. MVP技術構成

| 層 | 採用候補 | 役割 |
|---|---|---|
| UI | React + TypeScript + Vite | PC/Android共通UI |
| エディタ | CodeMirror 6 | Markdownソース編集、入力補完 |
| リッチ表示 | react-markdown + remark-gfm | Notion風の読みやすい表示 |
| ローカル保持 | IndexedDB | 下書き、送信待ち変更 |
| API | FastAPI | 読み書き、検索、競合検出 |
| ファイル | pathlib + atomic replace | NAS上のMarkdown直接操作 |
| 検索 | MVPはファイル走査、将来SQLite FTS5 | 全文検索 |
| メタデータ | YAML Frontmatter + Markdown本文 | タグ・タイトル等 |

### 3.1 エディタ選定方針

MVPではCodeMirror 6を採用する。Obsidianに近いMarkdown直接入力を確実に提供し、既存ファイルの未知の構文を編集エンジンが再構成するリスクを避ける。

Notion風の完全なブロック編集を追加する際はMilkdownとTiptapを比較する。採用条件は以下。

- Markdown import/exportで既存ファイルの意味・リンク・Frontmatterを保持する
- 未対応構文を削除・変換しない
- 編集前後のMarkdown round-tripテストに合格する
- IME日本語入力、Undo/Redo、モバイル入力、アクセシビリティに問題がない

それまでは「編集モード」と「Notion風表示モード」を分離し、表示切替だけで原文を変換しない。

## 4. UI仕様

### 4.1 全体レイアウト

- 左サイドバー: ワークスペース名、検索、新規ノート、フォルダ/ノート一覧、タグ
- 中央: ノートタイトル、本文、パンくず、保存状態
- 右ペイン（将来）: アウトライン、バックリンク、プロパティ
- 上部: 検索、コマンド、設定
- モバイル: 左サイドバーをドロワー化。本文を最優先し、右ペインは折りたたむ。

### 4.2 視覚デザイン

- Notionを参考にした明るいニュートラル基調、余白多め、控えめな境界線
- コンテンツ幅は読みやすい最大幅（約760–860px）
- タイトルは大きく、本文は十分な行間
- 保存状態は小さく常時表示し、色だけに依存しない
- ダークモード対応はMVP後半

### 4.3 編集表示モード

設定 `editor.presentation`:

- `source`: Markdown記号を見せる。CodeMirrorで直接編集。
- `notion`: Markdownをレンダリングした読みやすい表示。MVPでは閲覧表示であり、編集開始時にソース編集へ切り替える。
- 将来: `notion`をMilkdown等によるWYSIWYG編集に置き換える。原文保持テストに合格するまで有効化しない。

### 4.4 入力候補

入力中にカーソル位置に応じて候補を表示する。候補はキーボード操作可能とし、Escで閉じ、上下キーで選択、Enter/Tabで確定。

| トリガー | 候補 |
|---|---|
| `/` 行頭または空白直後 | 見出し、箇条書き、番号リスト、チェックリスト、引用、コード、区切り線、画像、表 |
| `#` | 既存タグ、新規タグ |
| `[[` | ノートタイトル・パス候補 |
| `@` | ノート・日付・コマンド候補 |
| Markdown記法 | `# `、`- `、`、`> `等の入力支援 |

MVPは `/` コマンド候補を実装し、タグ/ノート候補はAPI実装後に拡張する。

### 4.5 キーボード操作（初期案）

- `Ctrl/Cmd + K`: 検索
- `Ctrl/Cmd + N`: 新規ノート
- `Ctrl/Cmd + S`: 即時保存要求
- `/`: ブロック/書式候補
- `Esc`: 候補・ダイアログを閉じる

既存ブラウザ・OSショートカットと衝突する場合は設定可能にする。

## 5. Markdownデータ仕様

### 5.1 ファイル形式

- UTF-8
- 拡張子 `.md`
- LF/CRLFは読み込み時に検出し、保存時は原則として既存ファイルの改行コードを維持する（MVPではLFに統一する可能性があるため、実装前にテストする）
- YAML Frontmatterは任意。存在しないファイルへ勝手に追加しない。

例:

```yaml
---
title: 電磁気学
tags:
  - university
  - electronics
created: 2026-11-02
---

# 電磁気学

本文。URL: https://example.com
```

### 5.2 タグ

- Frontmatterの `tags` を標準形式とする
- 本文中の `#tag` は検索・候補用に解析するが、勝手にFrontmatterへ移動しない
- タグ階層は `project/keyboard` のような文字列で表現可能
- タグ管理UIは将来追加。ファイル名・本文はタグ変更時に破壊しない。

### 5.3 リンク・添付

- URLは通常のMarkdownリンクとして保持
- 内部リンク `[[ノート名]]` は原文のまま保持
- 画像・添付ファイルは将来 `Attachments/` 等の既存構成に合わせる
- ファイル移動時に内部リンクを自動修正する機能は、影響範囲プレビューとUndoを実装してから追加

## 6. 保存・オフライン設計

### 6.1 編集フロー

1. キー入力をエディタ内のメモリへ即時反映。
2. 変更ごとにIndexedDBへローカル下書きを保存（入力イベントをブロックしない）。
3. 300–700msのデバウンス後に送信キューへ追加。
4. APIへ `PUT /api/notes/{path}`。本文、ベースETag、変更IDを送る。
5. サーバーはETagを比較。一致すれば一時ファイルへ書き込み、flush後にatomic replace。
6. 成功応答の新ETagをIndexedDBに記録し、その変更IDをキューから除去。
7. 失敗時は下書きを保持し、指数バックオフで再試行する。

### 6.2 保存状態

- `保存済み`: サーバーが保存を確認
- `保存中`: 送信中
- `オフライン`: APIに到達できない
- `未保存`: ローカルに変更があり、サーバー未確認
- `競合`: サーバー側が別内容に更新されている
- `エラー`: 再試行不能なエラー。内容は保持する

「保存済み」はサーバーがNAS上のファイルへの書き込みを完了し、新ETagを返した場合のみ表示する。

### 6.3 冪等性

各変更にUUID `mutation_id` を付与。サーバーは直近の成功IDを記録し、同じIDの再送で二重処理しない。MVPでは軽量なSQLite台帳またはサーバープロセス内ではない永続ストアを使う。単一サーバー前提でも再起動をまたいで保持する。

### 6.4 競合検出

- GETで `ETag` を返す
- PUTは `base_etag` を必須にする
- 不一致なら `409 Conflict` とサーバー側最新本文・ETagを返す
- 自動的な最終書き込み優先は禁止
- UIは「サーバー版を見る」「自分の下書きを別名保存」「差分を確認」を提供する
- MVPは自動マージをしない

### 6.5 ブラウザ終了・端末再起動

IndexedDBへ保存済みの未送信内容は次回起動時に復元する。保存済みかどうかをサーバー応答で確認するまではキューを削除しない。ブラウザのストレージ消去・プライベートモード・端末故障に対する保証はできないため、NAS側バックアップは別途必須。

## 7. API仕様（v1）

### GET `/api/health`
サーバー・Vault接続状態を返す。

### GET `/api/tree`
フォルダとMarkdownファイルの一覧を返す。隠しフォルダ・システムフォルダは設定で除外可能。

### GET `/api/notes/{path}`
本文、ETag、更新時刻を返す。

### PUT `/api/notes/{path}`
Request:
```json
{
  "content": "# title\n",
  "base_etag": "sha256:...",
  "mutation_id": "uuid"
}
```
Response: 保存後ETag、更新時刻、mutation_id。ETag不一致は409。

### POST `/api/notes`
新規ノートを作成。既存パスへの上書きは禁止。

### GET `/api/search?q=...`
MVPはファイル走査。将来SQLite FTS5へ移行。

### セキュリティ
- Vaultルート外へのパストラバーサルを禁止
- シンボリックリンクを追跡しない
- `.env`の秘密情報をGitへ入れない
- APIトークンを設定可能にする
- CORSは許可オリジンを限定
- インターネットへの直接公開は禁止。外部接続はTailscale等に限定
- ファイルサイズ・リクエストサイズ上限を設定
- 実行ユーザーはVaultへの必要最小限の権限にする

## 8. 障害時挙動

| 障害 | 期待動作 |
|---|---|
| Wi-Fi切断 | 入力継続、IndexedDB保持、未保存表示 |
| API停止 | 入力継続、送信キュー保持 |
| NAS切断 | サーバーは保存失敗を返す。成功扱いにしない |
| ブラウザ再起動 | ローカル下書きを復元 |
| 同一ノートを別端末で更新 | ETag不一致で409、勝手に上書きしない |
| API再起動 | 永続キュー・mutation ID台帳から再送可能 |
| ディスク容量不足 | 保存失敗を明示し、ローカル内容を保持 |

## 9. セキュリティ・バックアップ

- NAS側のスナップショットまたは別媒体バックアップを必須とする
- サーバーはNASをマウント/共有アクセスするが、NAS管理者権限は不要
- 外部公開せず、Tailscale等の認証済みネットワーク内で使う
- APIトークンはブラウザの永続ストレージに平文保存しない方式を本番前に検討
- ログに本文・トークンを記録しない

## 11. 受け入れ基準

1. 1文字入力の反応がNAS応答時間に依存しない。
2. APIを停止しても編集中の内容を保持できる。
3. 再接続後、保存待ち変更が自動再送される。
4. サーバー保存確認前に「保存済み」と表示しない。
5. 競合時に片方の内容を無断で破棄しない。
6. 既存MarkdownのURL・Frontmatter・内部リンク・コードブロックが保持される。
7. WindowsとAndroidのブラウザで主要操作ができる。
8. NASを唯一の正本とし、同期フォルダを作らない。
9. Vaultルート外へのアクセスができない。
10. NAS切断時に成功を偽装しない。
